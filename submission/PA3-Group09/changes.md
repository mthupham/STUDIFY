## 2.2 Maintainability Requirements
> **Authors:** [Minh Thư] | **Reviewer:** [Thiên Phước, Kim Hằng, Gia Phúc, Khánh Linh] | **Editor:** [Minh Thư]

* Added a dedicated **Maintainability Requirements** section as **Section 6.8** under Other Product Requirements (Non-Functional Requirements).
* Added a minimum automated **unit and integration test coverage requirement of 70%**.
* Added a requirement for **static code analysis and linting**, with zero critical or blocking errors before code merging.
* Added a **Documentation Currency** requirement to ensure that centralized project documentation, including API specifications, architecture diagrams, and onboarding guides, is updated within 24 hours of any major release.

* Added **CI/CD requirements** for automated testing, incremental builds, and staging deployments.
* Defined a requirement for pull-request build and validation cycles to complete within **10 minutes**.

### Reason for Change

* Addressed TA feedback that the Vision Document lacked **Maintainability Requirements**.
* Defined measurable requirements to ensure the codebase remains maintainable and that critical system knowledge is distributed across the development team.
* Improved long-term project sustainability through automated testing, documentation, code reviews, and CI/CD practices.

## 2.3 Scalability Requirements
> **Authors:** [Minh Thư] | **Reviewer:** [Thiên Phước, Kim Hằng, Gia Phúc, Khánh Linh] | **Editor:** [Minh Thư]

### Changes

* Added a dedicated **Scalability Requirements** section as **Section 6.9** under Other Product Requirements (Non-Functional Requirements).
* Defined a requirement for the system to support at least **200 concurrent active users** during sustained study, timer, and quiz sessions.
* Added a requirement to maintain peak application-server CPU usage below **75%** under the target concurrent load.
* Added measurable **performance-under-load requirements**, including:

  * Average system API response time below **2.0 seconds (p95 < 2.0s)** for general requests under normal operating load.
  * Static asset delivery response time below **500 ms**.
* Added **API rate limiting** of **60 requests per minute per user** for standard endpoints.
* Added strict **daily usage caps** for external AI/LLM API calls to control external service usage and costs.

### Reason for Change

* Addressed TA feedback that the Vision Document lacked **Scalability Requirements**.
* Defined measurable system capacity and performance targets to ensure that Studify can support the expected number of concurrent users.
* Added rate limiting and AI API usage controls to reduce the risk of service overload, unexpected rate limits, and excessive external API costs.

## 2.4 Accessibility Requirements
> **Authors:** [Minh Thư] | **Reviewer:** [Thiên Phước, Kim Hằng, Gia Phúc, Khánh Linh] | **Editor:** [Minh Thư]

### Changes

* Added a dedicated **Accessibility Requirements** section as **Section 6.10** under Other Product Requirements (Non-Functional Requirements).
* Defined **WCAG 2.1 Level AA** as the accessibility compliance target for the Studify web interface.
* Added a requirement that key user interaction flows must be fully accessible through **keyboard navigation**.
* Specified keyboard accessibility for important interactions, including:

  * Flashcard navigation.
  * Flashcard flipping.
  * Pomodoro timer controls.
* Added visual accessibility requirements for **color contrast**, requiring:

  * A minimum contrast ratio of **4.5:1** for normal text.
  * A minimum contrast ratio of **3:1** for large text and UI components.
* Added a requirement to support **text scaling up to 200%** without loss of content or functional overlap.

### Reason for Change

* Addressed TA feedback that the Vision Document lacked **Accessibility Requirements**.
* Established measurable accessibility criteria to make the Studify interface more usable for a wider range of users.
* Improved consistency between the product's usability goals and accessibility expectations.

## 2.5 Data Quality Requirements
> **Authors:** [Minh Thư] | **Reviewer:** [Thiên Phước, Kim Hằng, Gia Phúc, Khánh Linh] | **Editor:** [Minh Thư]

### Changes

* Added a dedicated **Data Quality Requirements** section as **Section 6.11** under Other Product Requirements (Non-Functional Requirements).
* Added requirements for **AI Grading Accuracy and Validation**, requiring AI-generated CEFR scores to be benchmarked against human-evaluated control samples.
* Defined a minimum **85% score alignment rate** or alignment within a **±1 sublevel threshold** for AI-generated CEFR assessments.
* Added a **Deterministic Baseline Evaluation** requirement for diagnostic placement tests, ensuring that static multiple-choice components use pre-tested rule-based evaluation mechanisms.
* Added a requirement for **Proficiency Standard Uniformity**, ensuring that CEFR definitions from **A1 through C2** are consistently applied across progress tracking and score aggregation.
* Added a **Data Recovery and Loss Limits** requirement with:

  * **RPO ≤ 1 hour**.
  * **RTO ≤ 2 hours**.
* Applied data quality requirements to important user data, including study history, flashcard decks, progress metrics, and proficiency scores.

### Reason for Change

* Addressed TA feedback that the Vision Document lacked **Data Quality Requirements**.
* Established measurable criteria for the accuracy, consistency, standardization, and recoverability of critical learning data.
* Improved the reliability of AI-generated CEFR assessments and user progress tracking.
* Reduced the potential impact of data corruption or system failures on user learning history and progress information.
